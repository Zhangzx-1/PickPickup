# PickPickup
This project aims to develop a lightweight, cross-platform one-stop aggregation management tool for express and food delivery pickup codes (iOS Mini Program).


# 跨平台快递/外卖取件码聚合服务（Mini Program）项目策划书

## 一、 项目概述与立项背景

### 1.1 项目简介

本项目旨在打造一款轻量级、跨平台的**快递与外卖取件码一站式聚合管理工具（Mini Program）**。通过自动化数据提取与结构化解析技术，将分散在淘宝、京东、拼多多、小红书、抖音、美团等各大电商软件的快递取件信息及手机短信中的取件信息统一打通，为用户提供“集中展示、智能提醒、一键取件、履约归档”的全生命周期管理体验。

### 1.2 立项背景与痛点

* **信息碎片化严重**：用户日常包裹分布在不同的 小程序/小程序中（淘宝、京东、拼多多、小红书、抖音、美团等），每次取件需要在多个 小程序 之间频繁切换查找，耗费大量精力。

* **短信查找效率低**：许多末端驿站仅发送短信通知（包含复杂的取件码、驿站名称、手机尾号），用户在快递柜或驿站前翻找历史短信体验极差。

* **iOS 系统封闭瓶颈**：在 iOS 系统生态下，缺乏像 Android 端一样原生读取短信并生成弹窗卡片的功能，导致苹果用户获取取件信息的路径尤为冗长。

# iOS 生态“快捷指令自动化触发”技术实现与用户极简优化方案

## 一、 快捷指令（Shortcuts）自动化提取具体实现？

iOS 系统基于沙盒（Sandbox）安全与用户隐私保护机制，不允许第三方 小程序/小程序在后台默默直接读取用户的 SMS 短信内容。但苹果官方在 iOS 14 及以上系统中开放了系统级“快捷指令自动化（Personal Automation）”能力，使得通过系统原生的自动化机制提取短信成为可能。

### 1.1 完整数据流转架构

```
 [系统原生短信接收] 
        │
        ▼ (满足关键词条件：取件码/驿站/快递)
 [iOS 快捷指令系统触发器 (Automation Trigger)] 
        │
        ▼ (静默提取短信全文文本)
 [快捷指令解析脚本 (Shortcuts Action)] 
        │
        ├── 方式 A：小程序 自定义 URL Scheme (离线/本地处理)
        │    └─ 小程序name://parse_sms?text=编码后的短信内容
        │
        └── 方式 B：HTTP POST Webhook (云端/小程序处理)
             └─ 发送 JSON 请求至服务器 API：https://api.yourdomain.com/v1/sms/parse
        │
        ▼
 [小程序 / 小程序数据库更新] 
        │
        ▼
 [前端首页卡片即时刷新/锁屏小组件更新]

```

### 1.2 底层运行步骤拆解

1. **触发捕获（Triggering）**：系统收到新 SMS 短信时，iOS 系统的快捷指令守护进程（Daemon）检查短信内容是否包含指定的关键词（如：`取件码`、`驿站`、`快递`、`凭取件码`）。

2. **静默执行（Background Execution）**：若符合规则，系统在后台静默唤起预设好的快捷指令脚本，将短信文本作为变量输入（Input）。

3. **数据传输（Data Transport）**：快捷指令通过内置的“获取 URL 内容（Get Contents of URL）”或“打开 URL”动作：

   * **小程序 方案**：使用自定义 URL Scheme（如 `expressbox://import?content=...`）唤醒 小程序，直接在小程序本地解包。

   * **app / 云端方案**：将文本以 JSON 格式发送到后端 HTTP Webhook 接口，后端正则清洗出 `【取件码】`、`【快递公司】`、`【驿站/柜机位置】` 后保存至用户账号下的云端数据库，小程序打开时直接拉取最新卡片。

## 二、 用户必一次性极简配置快捷指令。**

苹果出于用户隐私与安全防范（防止恶意快捷指令静默偷窃隐私短信），在系统架构上做出了限制：

* **快捷指令动作本身（Shortcuts Actions）**：可以导出为 `iCloud` 分享链接，**实现一键导入**。

* **自动化触发器（Automation Trigger）**：即“收到短信时自动运行”这个**规则开关**，苹果**禁止**任何第三方应用通过代码或 Link 强制替用户自动勾选创建。

### 2.2 用户体验痛点

如果让用户自己从零打开 iOS 快捷指令 小程序 $\rightarrow$ 点击自动化 $\rightarrow$ 新建自动化 $\rightarrow$ 选短信 $\rightarrow$ 输关键词 $\rightarrow$ 粘代码 $\rightarrow$ 关掉运行前询问，**流程长达 8-10 步，转化率通常会低于 15%**。

## 三、 突破性解法：“一键安装 + 极简引导”方案

为了将用户配置门槛降低到**15 秒以内**，可以通过以下组合拳实现“接近一键”的流畅体验：

```
                    【极简配网/导入三部曲】
                               │
       +───────────────────────┼───────────────────────+
       │                       │                       │
[步骤一：一键导入快捷指令]   [步骤二：深层链接直达设置]   [步骤三：关掉“运行前询问”]
点击 iCloud 链接一键安装    快捷指令 URL Scheme 唤起     取消勾选确认弹窗
免去用户编写逻辑代码        自动跳到自动化新增页         实现完全“无感运行”

```

开发团队提前将写好的“短信解析与上传”快捷指令上传至 小程序le iCloud 服务器，生成官方分享链接： `https://www.icloud.com/shortcuts/xxxxxxxxxxxxxxxxx`

用户在 小程序 / 小程序内点击【一键配置快递自动同步】：

1. 唤起系统浏览器并跳转到快捷指令安装界面；

2. 用户只需点击最下方的 **【添加快捷指令】**（按钮 1）。

### 3.2 使用深度链接（Deep Link）直达自动化创建界面

在快捷指令导入完成后，小程序 内弹窗提示：“第二步：激活自动同步”。用户点击后，通过 iOS URL Scheme 直达快捷指令的“自动化”创建页： `shortcuts://automation`

3. 选取刚才导入的 **“快递自动同步”** 快捷指令，点击完成。

# iOS 快捷指令短信去重机制与微信服务号通知覆盖范围深度解析

---

## 一、 快捷指令自动化方案：新旧短信识别与去重机制

在 iOS “快捷指令自动化（Personal Automation）”场景中，解决**“如何区分本次提取的短信与历史短信”**以及**“如何防止重复写入/推送”**，需要从 **iOS 系统触发器机制**、**客户端（快捷指令本地）** 和 **服务端（后端 API / 数据库）** 三个层级协同设计。

### 1.1 iOS 系统触发器原生逻辑（从源头区分新旧）

首先需要明确 iOS 的底层触发逻辑：
* **事件驱动（Event-Driven）**：iOS 快捷指令的“收到短信”自动化是一个**实时事件触发器**。当且仅当系统**收到一封新 SMS 短信**并且匹配关键词时，系统才会唤醒自动化脚本。
* **增量传入（Incremental Pass）**：系统传给快捷指令的输入变量（`ShortcutInput`），**仅包含触发本次自动化事件的那一封新短信文本**，并不包含历史短信收件箱列表。
* **结论**：在正常系统自动触发的场景下，快捷指令天然接收到的就是“新短信”。

---

### 1.2 去重边界场景分析

虽然系统按事件触发，但在以下真实场景中必须进行去重防重：
1. **网络重试与超时（Network Retry）**：快捷指令通过 HTTP POST 发送 Webhook 到服务器时，若网络抖动超时，快捷指令可能进行重试，导致服务器收到多条相同请求。
2. **末端驿站/快递员重复发短信**：同一个包裹，快递员因为用户未取，在第 2 天再次发送了催取短信（取件码相同）。
3. **用户手动触发或导入历史短信**：用户手动运行脚本时，可能会把最近多条短信批量传给接口。

---

### 1.3 极简去重与历史比对逻辑架构

架构设计遵循 **“客户端轻量过滤 + 服务端幂等校验（Idempotency）”** 原则：

```
 [新 SMS 抵达 iOS 系统]
        │
        ▼
 [快捷指令提取文本] ──────────┐
        │                    │ (计算唯一指纹 MD5/Hash)
        ▼                    │
 [客户端本地缓存比对] ◄──────┘
  (Shortcuts Local JSON)
        │
        ├── 检查发现指纹已存在 ───► [拦截并静默终止Exit]
        │
        └── 指纹不存在 (新短信)
                │
                ▼
      [发送 HTTP Webhook]
                │
                ▼
      [服务端/数据库幂等校验]
        │
        ├── 匹配待取件状态卡片 ───► [更新收到时间/重发标记，不建新卡]
        │
        └── 无匹配卡片 ──────────► [新建待取件卡片 + 存入指纹库]
```

---

### 1.4 去重算法与具体设置方案

#### 方案 A：指纹哈希去重（Hash-based Deduplication）—— 防重复传输
1. **生成短信唯一指纹（Fingerprint）**：
   * 将提取到的原始短信文本加上收件时间（或发送方号码），进行 MD5 / SHA256 哈希计算：
     $$\text{Sign} = \text{MD5}(\text{RawText} + \text{SenderPhone})$$
2. **快捷指令本地缓存比对（客户端）**：
   * 在快捷指令中使用 **“获取 File (cache.json)”** 动作，读取本地存储的已处理 Hash 列表。
   * **逻辑**：`If cache.json contains Sign` $\rightarrow$ 退出；`Else` $\rightarrow$ 将 `Sign` 追加写入 `cache.json` 并继续执行 POST 请求。

#### 方案 B：业务主键匹配（Business Key Matching）—— 防重复卡片
在服务端对结构化提取后的数据进行**业务粒度去重**（即同一个包裹取件码只占用一张活动卡片）：

1. **提取核心字段**：`【快递公司】` + `【取件码】` + `【驿站/柜机名称】` + `【用户ID】`。
2. **数据库唯一性约束与状态机比对**：
   ```sql
   -- 检查当前用户下是否存在相同取件码且“未完成取件”的记录
   SELECT id, status FROM express_cards 
   WHERE user_id = :user_id 
     AND pickup_code = :pickup_code 
     AND station_name = :station_name 
     AND status = 'PENDING'; -- PENDING 表示待取件
   ```
3. **比对处理结果**：
   * **若存在待取件记录**：说明是快递员发来的“再次催取短信”，**不新建卡片**，仅更新该卡片的 `last_updated_time` 并设置“多次提醒”标识。
   * **若记录不存在，或已有记录状态为 `PICKED_UP`（已取件/归档）**：说明是新的包裹到达（或者是历史取件码循环再利用），**插入一条新的待取件记录**。
